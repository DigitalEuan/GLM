1. Executive Summary & Benchmark Architecture Overview

Context & Strategic Importance

Evaluating exact rational arithmetic architectures over high-dimensional geometric substrates requires testing regimes that are entirely free from the noise, approximation drift, and non-deterministic behavior inherent to traditional probabilistic language model evaluations. Candidate O1 (Question Set B) serves as a standardized, held-out evaluation benchmark engineered specifically for the Geometric Language Machine (GLM). The GLM architecture operates over \mathbb{Q}^{24}—a 24-dimensional computational domain rooted in the extended binary Golay code [24, 12, 8] and the Leech lattice \Lambda_{24}. Because the system completely rejects IEEE-754 floating-point calculations in favor of exact rational arithmetic using arbitrary-precision rational fractions (\mathbb{Q}), traditional evaluation suites that permit minor numerical drift or non-deterministic response variations are fundamentally incompatible. Candidate O1 establishes a formally verifiable, held-out test harness that assesses exact arithmetic state transitions, geometric boundary constraints, multi-surface routing, and multi-step reasoning chains without introducing empirical approximation errors.

Three-Column Thinking (TCT) Standard

Every non-refusal evaluation item within Candidate O1 mandates a synchronized Three-Column Thinking (TCT) response structure. This operational standard guarantees that semantic reasoning, formal mathematical state, and computational execution remain strictly linked and independently verifiable:

1. Column 1 (Language): A plain English, step-by-step conceptual reasoning chain establishing the contextual and physical semantics of the query.
2. Column 2 (Mathematics): The identical logical and computational transformations rendered as exact symbolic or rational equations over \mathbb{Q}, \mathbb{Z}, or \mathbb{F}_2 (e.g., using explicit rational fractions Fraction(p, q) rather than decimal approximations).
3. Column 3 (Re-Derivation Script): A dynamically generated, self-contained Python script string. When executed in an isolated interpreter subprocess (python3 -I) without shared memory or external imports, this script independently computes Column 2, returning an identical typed value and verifying the assertion.

Evaluation Scoring Protocol

Candidate O1 enforces a deterministic, asymmetric scoring protocol tailored to exact formal systems. Unlike probabilistic LLM evaluation schemes that rely on continuous semantic similarity metrics (such as BLEU, ROUGE, or cosine distance over embeddings), Candidate O1 evaluates candidate responses against discrete ground-truth assertions:

\text{Score}(Y, Y^* ) = \begin{cases} +1 & \text{if } Y = Y^* \text{ (Exact value and type match over } \mathbb{Q} \text{ with script verification)} \ +1 & \text{if } Y = Y^* \text{ (Correct refusal with exact matching named refusal code)} \ -1 & \text{if } Y \neq Y^* \text{ and } Y \neq \text{Refusal (Confidently wrong answer)} \ 0 & \text{if response is missing, unparsed, timed out, or raises execution exceptions} \end{cases}

In execution edge cases where Column 3 times out (exceeding the strict 5.0-second execution boundary), encounters an unhandled runtime error, or returns a non-zero exit code, the response receives a score of 0 if unparsed or missing, and -1 if the execution fails an explicit verification assertion or returns an incorrect typed value.

When an input vector traverses beyond the unique decoding radius of the substrate, violates physical junction boundaries, or encounters under-determined linear systems, the machine must refuse with an explicit, named error code. Category 1: Agree Channel Metrics & Pair Census (Marks G1–G8)

Category 1 evaluates the channel measures for the second reading (agree(y_1, y_2)), wherein a single carrier is subjected to two independent read operations at a declared bit-flip rate p. The truth is drawn uniformly from the 4,096 Golay codewords, and each bit of both reads flips independently at rate p.

The pair model evaluates the set of resolved pairs: R = \{ (\lambda_1, \lambda_2) : \text{wt}(\lambda_1) \le 4, \, \text{wt}(\lambda_2) \le 4 \} \setminus \{ \text{both wt } 4, \, \lambda_1 \cup \lambda_2 \text{ inside one octad} \}

By exploiting the action of the Mathieu group M_{24} and verified code automorphisms, the 164,051,805 total pairs in set R (calculated exactly as 12,951^2 - 3,676,596) are collapsed into 62 census groups exhibiting 28 distinct distance histograms over the 4,096 codewords. A fine key structure defined by the 5-tuple: (\text{wt}(\lambda_1), \, \text{wt}(\lambda_2), \, |\lambda_1 \cap \lambda_2|, \, m, \, e) collapses the pair confidence calculations into exactly 63 values without splitting a single histogram class (whereas a coarse 3-tuple key causes 9 class splits).

Four verified automorphism group generators generate a single orbit on coordinate subsets of sizes 1, 2, 3, and 4 (transitive action). Category 2: Confidence Floors & Rate Estimation (Marks F1–F7)

Category 2 assesses the confidence floor hunt and rate estimation dynamics over the six primary single-read stages: the complete decoder and the context stage (resolve) across the case sets S_2, S_4, S_8, S_{16}, S_{32}. A confidence threshold t is defined as working at rate p if and only if it satisfies two strict bounds:

1. The Promise: P(\text{wrong} \mid \text{answered}) \le 1 - t
2. The Cost Clause: Retention P(\text{right}, \text{answered at } t) / P(\text{right}, \text{unfloored}) \ge 9/10

For unfloored queries, the response uses a graded answer confidence band based on exact posterior probabilities:

* Near-certain: Posterior \ge 999/1000
* Confident: Posterior \ge 99/100
* Probable: Posterior \ge 9/10
* Uncertain: Posterior < 9/10

Rate parameter robustness analysis shows an asymmetric hazard:

* Overdeclaration (p/2): Overdeclaring the bit-flip rate (computing confidence at p while true errors occur at p/2) keeps the promise in 100\% (210/210) of grid cells.
* Underdeclaration (2p): Underdeclaring the bit-flip rate (computing confidence at p while true errors occur at 2p) breaks the promise in 30 out of 210 cells. For example, declaring p = 1/10 with a floor of t = 9999/10000 under true rate p = 1/5 promises a residual error of 0.0001 but delivers 0.0116. Consequently, rate estimation guards must default to higher rate estimates when uncertainty exists.

Category 4: Stepwise Reasoning, Reverse TCT, & Dialect Loops

Category 4 evaluates multi-step chained queries, symbolic language generation, integer decision procedures, and Python dialect loops:

1. Stepwise Planner Chains: Multi-step reasoning where intermediate outputs feed subsequent derivations. The planner verifies that all input givens are consistent (INCONSISTENT_GIVENS) and that all licensed derivation paths converge to identical values (DERIVATIONS_DISAGREE). Unasked intermediate steps are stitched automatically.
2. Reverse Three-Column Thinking (Reverse TCT): Generating Column 1 (Language) directly from Column 2 (Mathematics) using a prefix-first grammar that guarantees unique readability. Tested operations include say, equivalent, paraphrase, negate, solve, entails, and bounds.
3. Integer Omega-Test Elimination Mechanics: Entailment checks over \mathbb{Z} require specialized integer Fourier-Motzkin elimination rather than continuous real bounds checks over \mathbb{Q}. In continuous space \mathbb{Q}, the inequality 2x \ge 5 yields x \ge 2.5, which does not entail x \ge 3. Over integers \mathbb{Z}, Fourier-Motzkin elimination tightens fractional bounds using ceiling operations (\lceil 5/2 \rceil = 3). When real elimination leaves fractional bounds open, the Omega test executes real and dark shadow calculations alongside exact splinter searches across discrete residues. If splinter depth limits are exceeded without resolving an integer point, the system issues an INTEGER_UNDECIDED refusal. Column 3 scripts cannot rely on continuous real relaxations; they must carry explicit Farkas refutation certificates—linear combinations of integer constraints with non-negative integer coefficients proving refutation—re-verifying integer entailment directly within the subprocess.
4. Python Dialect Loops: Programmatic execution incorporating dialect builtins:
  * derive(target, (given_1, val_1), ...)
  * ask(question_string)
  * solve(var, equation_string)

These builtins allow dynamic control loops (e.g., iteratively incrementing resistance until derived current drops below a target threshold) while maintaining exact rational re-verification scripts.

Subprocess Execution Protocol

Every Candidate O1 test vector evaluated as VERIFIED_TRUE must supply an executable Python script string in Column 3. Verification harness execution adheres to the following execution rules:

1. Process Isolation & Environment Contract: The verification harness executes Column 3 in an independent Python subprocess using python3 -I (isolated mode). Isolated mode disables user site-packages, environment variables (PYTHONPATH), and standard script directory injection, eliminating shared memory or ambient state.
2. IPC / Stdout Communication Protocol: The harness invokes the interpreter via python3 -I -c "script_body". The script must execute entirely within Python's pure standard library (fractions, math, sys) without external third-party dependencies. Upon completion, the script must output a structured string to stdout matching the standard format KEY=VALUE VERIFIED True or REFUSAL_CODE=CODE VERIFIED True.
3. Verification Criteria: An entry is marked VERIFIED True if and only if:
  * The subprocess terminates with exit code returncode == 0 within a strict 5.0-second execution window.
  * Standard output contains the exact string VERIFIED True.
  * The computed output matches Column 2 identically in value and type (e.g., fractions.Fraction equality rather than floating-point approximation).
  * Any mutated certificate or altered mathematical claim triggers an assertion error, resulting in non-zero exit and immediate rejection.
